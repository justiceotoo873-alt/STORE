# @thetieguy — separate online store and secure Paystack auto-confirmation

**Deploying this store:** follow **[`DEPLOY-STORE.md`](DEPLOY-STORE.md)** for the SQL order, standalone Vercel project settings, environment variables, Paystack webhook, post-deploy verification and a fix table for common Vercel build errors. The wider two-project handoff (dashboard + store) is in [`../deploy/DEPLOY.md`](../deploy/DEPLOY.md).

The website is a separate Next.js/Vercel project from Athena's staff dashboard. It loads **real** products and prices from the latest Supabase project, sends customers to Paystack's hosted checkout, and **automatically confirms securely verified Paystack payments**. Athena does **not** read a screenshot or decide that money arrived. Staff handle *only exceptions, fulfilment and refunds*.

**Current state (30 September 2026):** The website, Athena merchandising tools and **both** SQL migrations have been tested **locally only**. Neither migration has been applied to live Supabase; server credentials, the production origin and actual delivery rates have not been supplied. Consequently the preview intentionally shows no made-up product prices and cannot take a real payment. **Do not treat payments as live before configuring and testing the deployed site.**

## How automatic confirmation works

1. The server takes a guest checkout request, ignores client-supplied prices, rereads prices/stock in PostgreSQL, creates an order with a unique Paystack reference and a 30-minute stock hold, then initializes **hosted** Paystack checkout with the exact GHS amount. The buyer's card/MoMo details never reach this site.
2. On a Paystack `charge.success` webhook, the server first checks its **raw-body HMAC-SHA512 signature**. On the customer return, it requires the browser's private checkout token. A daily protected reconciliation backstop can also check missed callbacks. **All three paths use the same server-to-server Paystack Verify call**, never the webhook/redirect payload as proof.
3. The server checks the transaction's `data.status === 'success'`, test/live mode, unique order reference, **integer pesewa amount**, GHS currency, customer email and order ID metadata. PostgreSQL independently compares the immutable order data again in a **service-role-only** RPC.
4. If the payment time is within the stock hold and every product can still be fulfilled, that **one atomic database transaction** marks the payment confirmed, records `confirmation_source='paystack'`, writes an append-only audit event and deducts stock **exactly once**. Retries or simultaneous webhook/return/cron calls cannot repeat the deduction. Staff can now prepare the order; **payment confirmation never marks it delivered**.
5. Invalid/missing Paystack time, a late charge, a mismatched amount/details or unavailable stock **never auto-confirm**. Mismatches, late charges and potential refunds appear in Athena's **Online store → Needs review**. A person can check a verified exception in Paystack before a manual override, or handle a refund in Paystack. **No refund is issued automatically.** Mismatched/underpaid charges cannot be marked paid by the dashboard's exception button.

**Scope:** This automatically handles **all Paystack transactions initialized and uniquely linked by this website**. The older WhatsApp/manual orders currently have *no* authenticated, order-specific Paystack checkout link. Arbitrary Paystack payment links and direct MoMo transfers cannot safely be mapped to those orders by guessing a reference or reading a screenshot; they remain manual. To automate future WhatsApp-order Paystack payments, create an order-linked checkout link through the **same server/verification logic**—not a second Paystack account or n8n workflow. Do not claim those payments are automated until such a link has been built and tested.

## Merchandising controls

- **Unlimited listings, finite stock:** Add as many real products as needed in Athena → Products; the customer collection is server-paginated (24 listings per page), with database-wide category filters, search and sorting. Checkout limits each bag to eight product/size options and rechecks finite stock and existing holds in PostgreSQL. Published out-of-stock items cannot be purchased. Product images/prices come from the real catalog, not the lookbook or test fixtures.
- **Offers:** Athena → Merchandising supports case-insensitive codes and automatic offers, percentage or fixed-amount product discounts, optional free delivery, active/scheduled dates, all/products/categories eligibility, minimum basket subtotal, total redemption caps and per-email caps. Checkout compares the best **single** eligible offer (it does not stack offers), reserves a limited redemption atomically, and saves the charged price and offer snapshot on the order. Quotes are indicative until checkout revalidates; Paystack settlement is verified against that immutable charged amount. “Free delivery” waives **only an actual configured delivery-zone fee**; when no delivery rate has been configured the charge still says “quoted and paid separately.” Discounts do not make a zero-pesewa transaction.
- **Storefront settings:** Staff can edit announcement banner, hero wording/colour treatment, promotional banner/image preset and linked collection in Merchandising. The approved burgundy/gold design and tie imagery remain available without adding sample products. Customer-facing settings are read through a restricted catalog RPC; staff-only promotion rules and charts are not public tables.
- **Size guides:** Staff enter their **own** chart columns, rows, units and notes for a category, with an optional product-specific override. Only published charts appear on the product detail; a product override wins over the category default. There are **no fabricated measurements**.
- **Stock attention:** A configurable `low_stock_threshold` per product drives dashboard-only low/out-of-stock attention. Sell-through, restock and threshold changes create/resolve staff alerts; failed stock-limited checkout attempts add a blocked-order event without capturing a payment. Athena may queue eligible staff merchandising drafts while offline but replays them only after version checks; a conflict must be reviewed rather than overwriting another device. No customer or WhatsApp/email notification is sent.

## Activate it, in order

1. Back up and inspect the live schema, RLS/policies, existing store objects, triggers, settings row and product ID type. **After explicit owner approval**, an administrator can apply `../supabase/migrations/20260930_online_store_paystack.sql` **then** `../supabase/migrations/20261001_store_merchandising.sql`, in that order, to project **`jatxzdmrasozbipsfmqy`**. Both are **currently unapplied**. The first is a *fresh create* and rejects pre-existing store objects; the second is a follow-up, not a standalone migration. They add separate private `store_*` tables and restricted RPCs without rewriting existing manual/WhatsApp orders or customers. Do **not** paste disposable SQL fixtures into the live editor, rerun either migration blindly, or run `supabase/schema.sql` over your existing data. If `public.settings` was dropped, review/apply the separately unapplied `../supabase/migrations/20260929_recreate_deleted_settings_uuid.sql` first, then set availability to **Available** in Athena.
2. Deploy the store as a **new Vercel project** with Root Directory `online-store`, Framework Next.js. Keep the existing Athena dashboard as a separate project. Set the six variables below in Vercel's private environment configuration—not in HTML, Git, or chat. Use a **Paystack TEST** key first. Production `STORE_ORIGIN` must exactly match the customer-facing HTTPS origin.
3. Configure Paystack's webhook URL as `https://YOUR_STORE_DOMAIN/api/paystack-webhook`. The store supplies its own `https://YOUR_STORE_DOMAIN/order/return` callback to Paystack. Paystack itself shows the card/MoMo methods enabled for **your** merchant account. A browser return alone never proves a payment.
4. Deploy/update Athena with its **browser-safe** `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (or anon key). Log in as a user listed in `staff_users`. Open **Merchandising** for banners, storefront copy/hero, scheduled discounts, category/product size charts, and stock-alert events; use **Products** for published stock, featured listings and each item's low-stock threshold. **Attention** shows current low/out-of-stock products and stock-blocked checkout events. Open **Online store** for Paystack orders and exceptions. Existing manual/WhatsApp order/payment totals stay separate to avoid double counting. Staff still mark orders ready/delivered and handle refunds.
5. Enter only *actual* GH₵ delivery fees under **Online store → Delivery zones & rates**. No fictional zones, promotions, size measurements or product records are seeded. For other delivery addresses, Paystack charges **products only**; the site clearly says delivery is **quoted and paid separately**. Pickup has no delivery fee. Enter real size measurements before publishing a chart and confirm the category label matches your products.
6. Place **real Paystack test-mode transactions** on the deployed HTTPS site. Verify immediate webhook and customer return; repeat a signed webhook and the status check to confirm **one** stock deduction and **one** audit event. Check failed/mismatched amounts, a missing webhook (protected backstop), late payment, stock-blocked checkout, pickup/unknown delivery zones, valid/invalid/expired offers, competing redemptions and scheduled start/end. Confirm audit mode is `test` before changing to `sk_live_...`. Only switch to live after the merchant account, webhook, staff exception queue and origin are verified.

### Store-project Vercel environment variables

| Name | Purpose |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Public Supabase project URL: `https://jatxzdmrasozbipsfmqy.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | This project's **public** publishable/anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | This **same** project's server-only service-role key; **NEVER** `NEXT_PUBLIC_` |
| `PAYSTACK_SECRET_KEY` | Server only; `sk_test_...` for testing, then `sk_live_...` once validated |
| `STORE_ORIGIN` | Exact HTTPS deployed store origin, no trailing slash/path |
| `CRON_SECRET` | Random **32+ character** server-only secret for missed-webhook reconciliation |

The included `vercel.json` schedules `/api/reconcile-pending` **once daily around 07:00 UTC** (Hobby timing may vary within the hour); it is compatible with Vercel Hobby's scheduling limit; **webhooks normally confirm immediately**. Vercel automatically sends `Authorization: Bearer $CRON_SECRET` to the protected route. The job examines a bounded number of pending orders from the previous 72 hours. If you use a paid Vercel plan, you may schedule a more frequent backstop, but never expose the route without a secret. The daily job does **not** replace webhook monitoring; Vercel does not retry a failed cron invocation. Vercel Preview deployments with a different origin cannot start a checkout when `STORE_ORIGIN` points to production; that is intentional.

## Local checks (no live Paystack charges or Supabase changes)

```bash
cd online-store
npm ci
npm run typecheck
npm test
npm run test:routes            # fake Paystack/PostgREST HTTP test; no other Next process running
npm run build                  # clean production build after the dev-based route test
npm run dev                    # http://localhost:3000
# With the preview running: node tests/ui-smoke.mjs
```

The browser smoke test intercepts catalog, config, size charts, offers and checkout with clearly **local-only fixture data**. Run `../tests/sql/run_local_online_store_tests.sh` on a **disposable LOCAL PostgreSQL cluster only**; it recreates `athena_online_store_test` and checks the original payment/security regressions plus merchandising scope, scheduled/capped offers, discounts on verified settlement, paginated catalogs, threshold events and UUID/bigint schema compatibility. **Never paste fixtures into the live SQL Editor.** `../tests/sql/assert_auto_concurrency.sh` additionally checks two simultaneous confirmations. The standalone Athena HTML and dashboard browser tests exercise staff merchandising edits, offline replay/conflicts, alerts and payment exceptions (`npm run test:html` from the project root).

**Security and operations:** The anonymous role can execute only a limited public catalog RPC. Checkout/status tables and the append-only payment audit are staff-private; server-only RPCs reject anon/authenticated callers. A checkout token hides customer status from other browsers. If a charge is pending or a webhook fails, **do not tell the customer to pay again** without checking the Paystack merchant dashboard. Auto-confirmation is about *payment*, not auto-fulfilment or auto-refunding. Rotate any exposed server key immediately. At higher traffic, add an edge WAF/rate limiter in addition to the existing database checkout-attempt cap.
